## Bundle offline para Basic Memory y Serena (2026-11-22)

- **Causa de la instalación incompleta:** `tools install` trataba la existencia de cualquier shim como instalación final y salía sin comprobar versión; `install.sh`/`install.ps1` descargaban `uv`, intérpretes y paquetes durante la instalación. En Fedora, una versión vieja podía quedarse instalada y la vista previa solo explicaba que los extras se descargarían después.
- **Cambio en `vdev`, publicado como PR #36 → `dev`:** `packaging/build_required_tools.py` fija Basic Memory `1.0.0` (Python 3.12) y Serena `2.1.0` (Python 3.13), genera locks con hashes y construye wheelhouses offline por plataforma. Las distribuciones fuente se convierten a wheels; sus hashes se añaden al lock. La resolución evita habilitar prereleases globalmente. El identificador del bundle incorpora su contenido. Los assets Linux x86_64, Windows x86_64 y macOS arm64/x86_64 quedan en el manifiesto con SHA-256. Los instaladores gráficos Linux/macOS los llevan incluidos; el MSI los incluye como archivos y `install.ps1` descarga el ZIP verificado.
- `chxchx-tech tools install --bundle DIR` valida el manifiesto, conserva el bundle bajo datos persistentes del usuario y fuerza la actualización con `uv --offline --no-index --no-python-downloads`; los shims se reinstalan aunque ya existan. Los intérpretes no quedan dentro de `/tmp` ni de la carpeta versionada del MSI. Se conserva el bundle persistente al desinstalar porque los entornos de `uv` lo necesitan.
- Vista previa nueva: descarga y compara SHA-256 del bundle y dice que las herramientas ya existentes se actualizarían offline. El instalador aún necesita conexión para descargar Studio y componentes generales; Basic Memory/Serena no consultan PyPI durante la actualización.
- **Validado localmente:** `cargo test --locked --features node` (644 + 36 + 6 + 22: 708 pasaron, 1 ignorada), `cargo clippy --locked --all-targets --features node -- -D warnings`, `cargo check --locked --no-default-features --features cli`, `cargo fmt --all -- --check`; `packaging/tests` (39 pasaron, 1 omitida); `cargo test --locked -p chxchx-remote` (21), clippy WASM y `scripts/build-remote.sh` (516 KB comprimidos). `bash -n`, compilación sintáctica Python, YAML y `git diff --check` también pasaron. Se construyó el bundle Linux real (223 MB comprimido), se instaló sin red y se sustituyeron shims antiguos; `basic-memory --version` devuelve 1.0.0 y `serena --version`, 2.1.0. El primer build descubrió y corrigió las rutas relativas de `uv` y la falta de wheel de `pybars3`.
- **Pendiente antes de integrar/publicar release:** el PR #36 está abierto y mergeable; después de integrarlo en `dev`, `release.yml` debe validar los builds nativos de Windows/macOS, la inclusión del bundle en MSI/DMG y el smoke test MSI. No hay `pwsh` disponible aquí. No se publicó un release nuevo; este cambio tampoco hace que el actualizador in-app de Studio `0.6.3` lea el manifiesto nuevo. Esa instalación se migra una vez con el `install.sh` de la release nueva.
- No hay herramienta Basic Memory disponible en esta sesión; se dejó el checkpoint en estos archivos locales.

## Diagnóstico del manifiesto de actualización (2026-11-22)

- Se descargaron los assets públicos de `v0.7.1`. `studio-manifest.txt` incluye `schema_version`, `channel=stable`, `tag`, `commit`, `version` y 12 entradas `asset.*` con su `sha256.*`; OpenSSL confirmó que `studio-manifest.txt.sig` valida con `packaging/release-public-key.txt`. El MSI, ZIP de Windows y los cuatro DMG están publicados. El flujo omite a propósito `windows-setup` y el paquete Windows ARM64 es opcional.
- **Causa confirmada para la PC Fedora con Studio 0.6.3:** su diálogo ejecuta el bridge Python `bridge studio-update`; `old-version/src/chxchx_tech_lead/integrations/studio_update_feed.py` exige `asset.cli-wheel` y `sha256.cli-wheel`, y devuelve literalmente «El manifiesto de Studio está incompleto» si faltan. El manifiesto de `v0.7.1` publica `agent-adapter-wheel`, porque el wheel del CLI Python se retiró. Ese actualizador 0.6.3 no verifica la firma, así que el cambio de firma no es la causa; el contrato del manifiesto dejó de ser compatible. Falla antes de instalar y por eso conserva 0.6.3.
- **Migración:** en Fedora, usar el `install.sh` actual del release; primero ejecutar `curl -fsSL https://github.com/chxchx-dev/chxchx-tech-lead/releases/latest/download/install.sh | bash -s -- --dry-run --update` y, si la vista previa identifica la instalación estable existente, repetir sin `--dry-run`. El instalador nuevo reconoce el marcador del launcher 0.6.3 y consume `agent-adapter-wheel`. Después de pasar a Rust, Ayuda → Buscar actualizaciones solo anuncia y abre la página; la instalación se hace con el instalador. El instalador automático in-app de 0.6.3 no puede volver a funcionar con el manifiesto nuevo sin publicar un asset de compatibilidad del CLI Python.
