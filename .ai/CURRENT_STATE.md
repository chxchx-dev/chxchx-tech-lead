## Nodo local, acceso remoto y app web: H0–H5 hechas (2026-11-21)

- **Qué existe** (todo en `dev`; ver [ROADMAP-HIBRIDO.md](ROADMAP-HIBRIDO.md) y [ADR 0017](adr/0017-local-node-and-remote-access.md)):
  - `crates/chxchx-protocol`: tipos del contrato (trabajos, eventos, respuestas, dispositivos, roles). Compila a WASM.
  - `features/jobs`: cola persistente (instantánea + diario), `JobRunner` con idempotencia, cancelación, tope de 50 en cola y respuestas a permisos; los turnos de agente corren como trabajos. `chxchx-tech jobs run|list|show`.
  - **Nodo** (feature `node`, ya en el build por defecto y en los paquetes de release desde 2026-11-21; el comando es opt-in, nada lo arranca solo): `node start|status|stop`, API v1 en `127.0.0.1`, eventos por WebSocket, `node pair|devices|revoke|audit`, `node remote status|enable|disable` con Tailscale. Presupuestos medidos: 10,4 MiB en reposo, 0 de CPU, `health` p95 1,13 ms.
  - **App web** (`apps/remote`, Dioxus/WASM, 610 KB comprimida) servida por el nodo en `/`: proyectos, chat en vivo con permisos y preguntas, trabajos, dispositivos y ajustes; instalable, sin red al arrancar y con reconexión. QR de vinculación en `node pair`.
- **Seguridad:** [NODE-SECURITY.md](NODE-SECURITY.md) (autorrevisión; riesgos aceptados y lo abierto).
- **Verificado:** Linux (18 + 509 + 6 + 22 pruebas, tres pasadas; clippy con `--features node`; builds por defecto y `cli`; WASM) y de punta a punta con Tailscale 1.104.7 real pasando por la tailnet desde la propia PC.
- **Cliente web:** 26 pasos de navegador en Chromium 139 (`apps/remote/e2e`); carga 0,89 s (4G típico) y 2,49 s (Slow 4G).
- **No verificado:** el cliente en Safari/iOS y Firefox, prueba desde otra red (celular con datos móviles), Windows (ACL del token y archivos) y macOS, Codex/OpenCode/Claude reales a través del nodo, CI remoto de los últimos pushes.
- **H5:** Studio delega turnos al nodo (opt-in en Ajustes → Nodo local, que también inicia/detiene el nodo y gestiona dispositivos) y `node service install|status|uninstall` lo instala como servicio de usuario (verificado en Linux; macOS y Windows sin verificar). El nodo guarda el error de arranque en `start.log` de su carpeta.
- **H6:** `manager status|plan|apply|update|watch|recover|keygen`: inventario, supervisión con backoff y corte, recuperación en lista cerrada, actualización firmada con vuelta atrás (solo Linux x86_64; clave pública publicada) y auto-ajuste de concurrencia. `v0.7.1` estable se publicó el 2026-11-22; su manifiesto contiene 12 assets con sus SHA-256 y la firma Ed25519 valida con la clave del repo. Hallazgo de compatibilidad: el actualizador incluido en `v0.6.3` requiere `asset.cli-wheel`/`sha256.cli-wheel`, retirados al pasar a `agent-adapter-wheel`, y por eso da «El manifiesto de Studio está incompleto» antes de cambiar archivos; la firma no es la causa. Hay que hacer esa migración una vez con `install.sh --update`. En las versiones nuevas, Studio solo consulta la etiqueta y abre la página; Windows/macOS usan instaladores. Ver HANDOFF.
- **Herramientas requeridas (PR #36, `vdev` → `dev`):** el instalador prepara un bundle por plataforma con Basic Memory `1.0.0`, Serena `2.1.0`, locks con hashes, wheels, `uv` y Python 3.12/3.13. `tools install --bundle` actualiza instalaciones anteriores sin red y conserva los intérpretes en datos de usuario. Se construyó el bundle Linux real y se verificó la instalación/actualización offline, incluidos shims viejos. Los instaladores de consola verifican el SHA; el instalador gráfico Linux/macOS y el MSI incluyen el bundle. Windows/macOS siguen pendientes del CI nativo y PowerShell no está disponible en esta máquina. Ver HANDOFF.
- **Siguiente:** probar con un teléfono real y completar la QA de Windows/macOS según [TEST-PENDIENTES.md](TEST-PENDIENTES.md); H7 queda fuera del plan.

## `old-version/` eliminada; empaquetado con el servicio de agentes (2026-11-19)

- **`old-version/` ya no existe** (CLI Python, sus 560 tests, `uv.lock`, scripts). Lo que seguía vivo se movió o se reemplazó: `install.sh`, `install.ps1` y `release_assets.py` están en `packaging/` con sus tests (39); el servicio `services/agent-adapter/` (50 tests) sustituye al *wheel* del CLI heredado; `chxchx-tech tools install` (Rust) sustituye a `chxchx-tech install` de Python (Basic Memory y Serena con `uv tool install`, con detección del `uv.exe` y la carpeta `tools` del MSI).
- Instaladores: **se retiró `--cli-only`** (`-CliOnly` en PowerShell) porque instalaba el CLI Python como comando; el paquete completo ya trae `chxchx-tech` y `chxchx`. El wheel del manifiesto pasa a `agent-adapter-wheel` (`chxchx_agent_adapter-*`), el binario instalado es `.venv/bin/chxchx-agent-adapter` y las variables de los launchers y shims, `CHXCHX_AGENT_ADAPTER`. La versión del release se lee de `Cargo.toml`.
- Windows: el lanzador `chxchx-python-helper` pasó a `chxchx-agent-adapter` (`python -m chxchx_agent_adapter`, feature `agent-adapter-launcher`); `build_windows_msi.ps1` empaqueta el wheel del servicio (sin dependencias de terceros), la acción del MSI `InstallRequiredTools` ejecuta `bin\chxchx-tech.exe tools install`, y `test_windows_msi.ps1` / `verify_windows_binaries.ps1` comprueban el nuevo lanzador. `release.yml` construye el wheel del servicio (`agent-adapter-wheel`), ya no compara versiones con un pyproject y ejecuta los tests de `packaging/`.
- Verificado en Linux: formato, Clippy estricto, `cargo test --locked` (376 unitarias, 6 catálogo, 22 flujos), `cargo check` de los builds `cli` y `agent-adapter-launcher`, `pytest` del servicio (50) y de `packaging/tests` (39: `install.sh` completo con `uv` y release falsos, manifiesto y generador del MSI). **No verificado: `install.ps1`, `build_windows_msi.ps1`, `test_windows_msi.ps1` ni el MSI (solo PowerShell en el runner de Windows), ni un release real con el servicio empaquetado, ni macOS.** `install.ps1` conserva ramas `$CliOnly` inalcanzables que conviene limpiar al probarlo en Windows.
- Siguiente: ejecutar `release.yml` a mano (`publish` desactivado) y revisar los artefactos y los instaladores en Windows y macOS; probar el servicio con Codex y OpenCode reales; QA nativa.

## Ruta heredada del chat retirada; qué falta para borrar `old-version/` (2026-11-19)

- Rust ya no usa el CLI Python para nada en tiempo de ejecución: se eliminó el protocolo heredado del chat (sondeo, lanzamiento y control de `chxchx-tech agent chat`), `find_cli`/`legacy_cli`/`supports_chat` y el plumbing `cli` de Studio. Claude corre desde Rust; Codex y OpenCode, desde `services/agent-adapter/`, y sin el servicio el chat dice cómo conseguirlo (`uv sync` en `services/agent-adapter` en un checkout, o `CHXCHX_AGENT_ADAPTER`). Los tests Studio de OpenCode usan un servicio falso. Verificado en Linux: formato, Clippy estricto y 371 unitarias estables en tres ejecuciones.
- **Lo que queda para poder borrar `old-version/`: empaquetado y release.** Decisiones del mantenedor: el actualizador solo avisa y abre la descarga (hecho), y el servicio viaja con su propio runtime. Hallazgos al intentarlo (no se tocó nada de esto, se revirtió un intento a medias):
  1. `old-version/scripts/install.sh` (687 líneas) e `install.ps1` (532) instalan el *wheel* del CLI Python en un `.venv` con `uv` y exportan `CHXCHX_TECH_CLI`. Hay que cambiarlo por el wheel del servicio (`chxchx_agent_adapter-*`, binario `chxchx-agent-adapter`, variable `CHXCHX_AGENT_ADAPTER`, clave de manifiesto `agent-adapter-wheel`).
  2. El modo `--cli-only` de los instaladores instala **el CLI Python como comando `chxchx-tech`**; hay que reemplazarlo por los binarios Rust del paquete sin la app de escritorio.
  3. Los instaladores ejecutan `chxchx-tech install` (Python, `integrations/installers.py`) para instalar Basic Memory y Serena con `uv tool install`; ese comando se retiró del CLI, así que hace falta un equivalente Rust (por ejemplo `chxchx-tech tools install`) o que el instalador llame a `uv` directamente.
  4. `release_assets.py` toma la versión de `old-version/pyproject.toml` y empaqueta el *wheel* `cli-wheel`; la versión debe venir de `Cargo.toml`. `release.yml` compara versiones con el pyproject, construye el wheel en `old-version` y ejecuta los tests de instaladores allí.
  5. MSI de Windows: `scripts/build_windows_msi.ps1` empaqueta un runtime Python privado con el wheel heredado y `src/bin/chxchx-python-helper.rs` lo lanza (`python -c "from chxchx_tech_lead.cli import app"`); debe pasar a `python -m chxchx_agent_adapter` como `chxchx-agent-adapter.exe` (el adapter Rust ya busca ese nombre junto al binario). Afecta también a `generate_windows_msi_wxs.py`, `test_windows_msi.ps1`, `verify_windows_binaries.ps1`, `build.rs` y `Cargo.toml`.
  6. `src/interfaces/installer.rs` incrusta `old-version/scripts/install.sh` con `include_str!`.
  Los scripts y sus tests (`old-version/tests/installers`) deben moverse a `packaging/`. Los instaladores de Linux/macOS se pueden probar con `pytest`; los de Windows (PowerShell/MSI) solo se verifican en el runner de Windows, así que conviene hacerlo con CI a mano.
- Después: borrar `old-version/` (y su `uv.lock`, tests y `.venv`), actualizar README/MANUAL y `.gitignore`.
